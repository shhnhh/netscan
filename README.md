# NetScan

Локальный сетевой сканер для iOS (альтернатива Fing без подписки). Находит
устройства в текущей Wi-Fi подсети через TCP ping-sweep и обогащает список
именами через Bonjour/mDNS.

## Как это работает (MVP)

- `NetworkInfo` — читает IP/маску интерфейса `en0` (Wi-Fi) через `getifaddrs`.
- `SubnetScanner` — параллельно (до 32 одновременно) стучится TCP-коннектом
  на несколько частых портов (`80, 443, 22, 445, 62078`) на каждый хост
  подсети; таймаут 0.6с. Отклик (успех или явный `ECONNREFUSED`) считается
  признаком живого хоста. Параллельно с портами на каждый хост шлётся ещё
  и `ICMPPinger` (unprivileged ICMP echo, тот же трюк, что у Apple
  `SimplePing`) — часть устройств (телефоны, IoT) не держит открытым ни
  один из проверяемых портов, но отвечает на пинг; без этого их видно не
  было. Своё устройство в список добавляется сразу, без пробинга — оно и
  так точно "живое".
- Во время скана `ContentView` показывает счётчик "проверено X/Y · найдено N"
  (данные из `SubnetScanner`'s `onProgress`) — иначе непонятно, идёт ли
  скан вообще или он просто ничего не находит.
- `BonjourScanner` — параллельно слушает объявленные mDNS-сервисы
  (`_http._tcp`, `_airplay._tcp`, `_ipp._tcp` и т.д.) для человекочитаемых
  имён устройств.
- SwiftUI: список найденных устройств → детали (IP, порты, отклик).

### Глубокое сканирование и безопасность

Часть проверок работает **автоматически** сразу после общего скана:
`SecurityAnalyzer` прогоняется по портам каждого найденного устройства, и
рискованные хосты подсвечиваются в списке сами (красный треугольник),
без ручных действий. Сверху списка — сводка "N устройств с потенциальными
проблемами" либо "явных проблем не найдено".

Из деталей устройства по кнопке **"Глубокое сканирование"** запускается
отдельный, более тяжёлый проход только по этому хосту, который дополняет
быстрый анализ баннерами:

- `DeepPortScanner` — стучится на ~44 порта (базы данных, RDP/VNC/Telnet,
  ADB, Elasticsearch/Memcached/CouchDB, RTSP/DVR-порты камер и т.д.), в
  отличие от `SubnetScanner` считает порт открытым только по реальному
  TCP-хендшейку (не по `ECONNREFUSED`).
- `BannerGrabber` — на открытых портах, где это уместно, делает один запрос
  (для HTTP — `GET /`, для RTSP — `OPTIONS`) и читает первый ответ/баннер.
- `SecurityAnalyzer` — правила двух видов. По портам: типичные проблемы
  конфигурации (открытый Telnet/2323, ADB, БД без пароля на виду —
  Redis/Mongo/Elasticsearch/Memcached, RDP/VNC/SMB, MikroTik Winbox, X11 и
  т.д.). По баннерам: сигнатуры конкретно опасных сборок (vsFTPd 2.3.4 с
  бэкдором, устаревшие OpenSSH/Apache/IIS, встраиваемый Boa из дешёвых
  камер). Плюс по RTSP/DVR-портам и строкам вида `hikvision`/`dahua`/`dvr`
  помечает устройство как вероятную камеру/видеорегистратор.

Это **полностью пассивная разведка**: один банер-граб на порт, без подбора
паролей, без эксплуатации найденного и без обращения к самому видео/аудио
потоку камеры. Инструмент для собственной сети — не для чужой.

Отдельно для RTSP-портов (554/8554) баннер-граббер шлёт `DESCRIBE` вместо
`OPTIONS` — по коду ответа (есть `401` или нет) видно, требует ли поток
пароль. Если не требует — это критичная находка в списке проблем
("похоже открыт без пароля"), но само приложение к потоку не подключается
и видео не показывает — только читает один текстовый заголовок ответа.

### Тест скорости сети

Третья кнопка в тулбаре — `SpeedTestView`. `SpeedTestService` гоняет
пинг/скачивание/отдачу против публичных, не требующих ключа эндпоинтов
`speed.cloudflare.com` (`__down`/`__up` — то же, чем пользуется их
собственная страница спидтеста): пинг — медиана трёх HEAD-запросов,
скачивание — до 50 МБ или 6 секунд (что раньше), отдача — 8 МБ случайных
байт (генерятся через `arc4random_buf`, не поэлементным Swift-циклом —
на 8 млн байт это ощутимая разница в скорости генерации).

### Платформа и роутер

- `NetworkInfo.hostAddresses` раньше **всегда** варьировал только последний
  октет в пределах "своего" /24, даже если реальная маска была шире (/22,
  /21…) — на подсети больше /24 сканировались только первые 254 адреса, а
  всё остальное молча пропадало. Теперь честная CIDR-арифметика по
  32-битному представлению IP/маски, лимит поднят до 512 хостов.
- Этот же более широкий диапазон вскрыл баг в `ICMPPinger`, который
  проявлялся как "находится ровно 512 устройств" (весь диапазон подряд,
  включая несуществующие адреса). Причин было две, чинились по очереди:
  (1) старый код считал **любые** пришедшие байты ответом "устройство
  живое", не проверяя тип ICMP; (2) сокет неприконнекчен, поэтому `recv`
  ловил **любой** ICMP, пришедший процессу — ответ, предназначенный одному
  из 32 параллельных пингов, или `Destination Unreachable` от роутера за
  мёртвый адрес. Итоговое решение: читаем через `recvfrom` в цикле до
  дедлайна и засчитываем только Echo Reply (тип 0, с разбором IPv4-заголовка
  как в `SimplePing` от Apple) **именно с того адреса, который пинговали** —
  чужие пакеты игнорируем и ждём дальше. Проверку identifier убрали: на
  `SOCK_DGRAM` ICMP ядро само перезаписывает это поле, так что она давала
  только ложные отрицания.
- Имена устройств теперь как у Fing, из двух независимых источников:
  `ReverseDNSResolver` (обратный DNS/PTR через `getnameinfo`) — но на
  практике это зависит целиком от роутера, и много каких роутеров PTR
  просто не отвечают (на одной реальной сети — 0 имён из 44 устройств,
  ни одно). Основной рабочий источник — `BonjourScanner`: раньше он
  просто показывал имя сервиса без адреса ("full IP correlation..." было
  прямо оставлено как TODO в коде), теперь реально резолвит IP через
  `NWConnection` к найденному mDNS-сервису и матчит имя на устройство в
  списке — большинство телефонов/принтеров/Apple-техники сами
  анонсируют своё имя по Bonjour, роутер тут ни при чём.
  Два дефекта, из-за которых на практике имя подхватывалось только у
  MacBook (Mac реально слушает TCP-порты, iPhone/iPad — почти никогда):
  - Резолв IP шёл через **TCP**-соединение к сервису — а `_device-info._tcp`
    и `_companion-link._tcp` (именно они несут имя iPhone/iPad/Watch)
    существуют только для обнаружения, за ними часто вообще не стоит
    сервер, так что TCP-хендшейк не завершался и IP не резолвился. Заменили
    на **UDP**: `NWConnection` по UDP становится `.ready`, как только mDNS
    разрешил адрес и есть маршрут — реального слушателя на порту не нужно.
  - AirPlay/RAOP (`_raop._tcp`) называет свои сервисы не просто "MacBook",
    а `<12 hex-цифр ID устройства>@MacBook` — это форма протокола, а не
    поломанная кодировка. `cleanServiceName` отрезает этот префикс, если
    он выглядит как 12 hex-символов перед `@`.
  Также добавлены типы `_companion-link._tcp`, `_rdlink._tcp`,
  `_homekit._tcp`, `_googlecast._tcp` — под iPhone/iPad/Watch, HomeKit и
  Chromecast/Android TV соответственно (список синхронизирован с
  `NSBonjourServices` в `project.yml`, иначе iOS сервис не отдаст).
- `SSDPScanner` — третий источник имён, независимый от Bonjour: UPnP/SSDP
  (multicast M-SEARCH на 239.255.255.250:1900, как это делают DLNA-клиенты)
  ловит телевизоры, роутеры, колонки и прочий IoT, которые mDNS вообще не
  говорят, но откликаются на SSDP-обнаружение с XML-описанием устройства,
  где есть `<friendlyName>`. На практике это то же самое имя, которое
  устройство показывает при сопряжении по Bluetooth — просто у большинства
  вендоров это одно имя устройства на все протоколы, а не три разных. Сам
  Bluetooth мы не слушаем и не можем: iOS не даёт связать BLE-идентичность
  конкретного устройства с его IP/MAC в Wi-Fi-сети, эти два радиоканала
  никак не коррелируют на уровне API.
- `LockdownClient` — четвёртый источник, и самый прямой из всех для iOS:
  каждый iPhone/iPad открывает TCP 62078 (`lockdownd`, тот же сервис, что
  используют iTunes/Xcode для Wi-Fi-синхронизации). Без какого-либо пейринга
  можно послать один `GetValue`-запрос (`Key: DeviceName`) в родном
  wire-формате lockdown (4 байта big-endian длины + XML plist) и получить
  в ответ ровно то имя, что задано на самом устройстве ("Fedor's iPhone") —
  никакого сопоставления по MAC/вендору не нужно, имя приходит прямой
  строкой. Срабатывает сразу при обнаружении открытого 62078 в основном
  сканировании.
- Имя-вендор: если ни hostname, ни Bonjour/SSDP-имени, ни lockdown-имени
  нет, но известен вендор
  по MAC — он и становится подписью устройства (как Fing показывает
  "Samsung Electronics" вместо голого IP). Такие устройства тоже считаются
  "распознанными".
- Список сортируется так, что распознанные устройства (есть имя — из
  DNS/Bonjour/вендора, включая "Это устройство"/"Роутер") идут сверху по
  алфавиту, а безымянные IP — ниже по возрастанию адреса.
- Новые устройства: `NetworkHistoryStore` запоминает MAC-адреса, виденные
  в каждой сети (ключ — адрес шлюза, чтобы смена Wi-Fi не помечала всё
  подряд новым). При повторном скане устройство, чьего MAC раньше в этой
  сети не было, получает зелёный бейдж **NEW** — тот самый сигнал "новое
  устройство в сети", как у Fing. Первый скан сети просто фиксирует
  базовый набор, ничего не помечая. Всё локально, ничего не уходит наружу.
- В строке устройства помимо имени видно IP, тип платформы, вендора (если
  не совпадает с подписью) и число открытых портов.
- `PlatformGuesser` — эвристика по портам, подстрокам в
  Bonjour-имени/hostname и вендору по MAC: Apple (62078/вендор Apple/имя),
  Windows (3389/NetBIOS+SMB), принтер (631 IPP/9100 RAW), ТВ/проектор
  (порт 7000 — это порт AirPlay-**приёмника**, то есть того, на что
  кастуют, а не того, кто кастует, плюс 8008/8009 Chromecast), IoT
  (вендор Espressif/Raspberry Pi/Tuya), игровая консоль (вендор Nintendo).
  Android просто получает нейтральную иконку телефона. Без
  TTL-фингерпринтинга это грубее, чем у Fing, но с иконками (SF Symbols не
  даёт логотипы Windows/Android — там нейтральные иконки, у Apple логотип
  есть).
- Роутер получает отдельный, более широкий проб (через `DeepPortScanner`)
  на предполагаемый IP шлюза, параллельно с общим сканом, и явно
  помечается `isGateway` — раньше он показывался в списке только если
  случайно отвечал на один из 5 портов быстрого свипа. Настоящий default
  route публичным API недоступен, поэтому пробуем по очереди два
  кандидата (первый и последний адрес подсети — роутеры у некоторых
  провайдеров СНГ сидят именно на последнем), **по одному за раз**: если
  первый ответил — вторым уже не пробуем, иначе в списке было бы два
  "роутера" сразу (реальный баг, который так и было на первой версии
  этого фикса).
- `SubnetScanner` отдельно ловит `ENETDOWN` на TCP-пробах — это
  задокументированный признак того, что разрешение "Локальная сеть"
  отклонено или зависло (по форумам Apple такое бывает даже после
  повторного включения в Настройках, лечится перезагрузкой телефона). Если
  это случилось, статус явно говорит "нет доступа к локальной сети"
  вместо того, чтобы молча показать пустой список, будто в сети никого
  нет.
- **Чего нет и не будет**: "Block device"/"Pause internet" (как в Fing) —
  это ARP-spoofing чужого трафика, у Fing это отдельная платная железка
  (Fingbox), а не сама программа с телефона; на iOS это и технически
  недостижимо без джейлбрейка, и по сути уже не сканер, а атака на чужие
  устройства в сети.

### MAC-адрес и вендор (как в Fing)

Читаем ARP-таблицу ядра — кэш соответствий IP→MAC, который ОС ведёт для
всех, с кем недавно общалась в локальной сети. Тот же механизм, что
`arp -a`: `sysctl` с `CTL_NET/PF_ROUTE/NET_RT_FLAGS/RTF_LLINFO`. MAC виден
только внутри своего сегмента (это L2), но нам ровно это и надо.

Тут два слоя граблей, оба выяснились на реальных сборках в CI. Сначала
пробовали на чистом Swift — не компилируется, `rt_msghdr`/`RTF_LLINFO` не
пробрасываются в Swift-оверлей `Darwin`. Переписали на Objective-C — и
всплыл второй слой: **`<net/route.h>` вообще отсутствует в iOS SDK**, даже
для C (`'net/route.h' file not found`), в отличие от macOS SDK. Поэтому
нужные структуры маршрутных сообщений (`rt_msghdr`, `rt_metrics`) и
константы (`NET_RT_FLAGS`, `RTF_LLINFO`) **объявлены руками прямо в
`ARPTable.m`** — это стабильный ABI ядра (layout 1:1 с XNU
`bsd/net/route.h`), он не меняется десятилетиями, потому что сам формат
данных от `sysctl` завязан на него. `sockaddr_dl` и MIB-константы в iOS SDK
есть, их не переопределяем. Ровно этот же приём (принести определения с
собой) используют open-source `MMLanScan`/`MacFinder` — только они копируют
целые заголовки из macOS SDK в репо, а тут объявлен лишь необходимый
минимум. Вся C-часть вынесена за bridging header (`NetScan-Bridging-Header.h`),
Swift зовёт её через `ARPResolver`.

Ключевой момент: ARP-кэш наполняется **как побочный эффект самого скана** —
пинг и TCP-коннекты к каждому адресу заставляют ядро отрезолвить MAC. Поэтому
таблицу читаем уже после свипа (и повторно через 2 секунды — часть записей
оседает в кэше чуть позже), и подмешиваем адреса к уже найденным устройствам.

Вендор (то самое "Поставщик: Intel" у Fing) — `MacVendorLookup` по префиксу
OUI (первые 3 байта MAC, назначаются IEEE производителям). Полная база IEEE
это ~35k записей на несколько мегабайт; встроена курированная выборка самых
ходовых бытовых префиксов (телефоны, роутеры, IoT, консоли, принтеры).
Известный MAC с префиксом не из выборки просто не покажет вендора — это не
ошибка, таблицу легко дополнить.

Честные оговорки: MAC **своего** телефона iOS прячет с iOS 7 (отдаёт
`02:00:00:00:00:00`) — но он нам и не нужен. На части версий/устройств и
чужие MAC могут прийти занулёнными — тогда просто не покажем MAC у таких
устройств (`00:00:00:00:00:00` отфильтровывается на чтении). Плюс если
переподпись через iLoader не сохранит доступ к маршрутным сокетам — MAC не
появится вообще; тогда напиши, разберёмся по факту.

### Инструменты безопасности

Экран за иконкой щита в тулбаре — Wi-Fi аудит, единственный инструмент из
этой категории, который реально работает на голом iOS без джейлбрейка и
без своего сервера:

- **Wi-Fi аудит** (`WiFiSecurityInfo`) — через `NEHotspotNetwork` смотрит
  **только ту сеть, к которой подключён телефон прямо сейчас**: SSID,
  BSSID, открыта она или защищена. Полного скана всех точек вокруг (как в
  Fing/классических Wi-Fi-анализаторах) на iOS для сторонних приложений
  **не существует** — Apple не даёт стороннему коду списки соседних APs,
  это одна из вещей, которая физически возможна только с джейлбрейком.
  Также сама iOS не сообщает приложениям точный протокол шифрования
  (WEP/WPA2/WPA3) — только факт "защищена / не защищена". Отдельно
  инструмент запоминает на устройстве, на каком BSSID видел каждый SSID
  раньше, и если знакомая сеть вдруг всплыла на новом железе — это
  сигнатура поддельной точки доступа (evil twin), выводится предупреждение.
- Требует `com.apple.developer.networking.wifi-info` entitlement (добавлен
  в `project.yml`) — обычная, не приватная возможность Xcode. Но по факту
  на реальном устройстве оказалось, что entitlement'а недостаточно: по
  [форуму Apple](https://developer.apple.com/forums/thread/684519)
  `NEHotspotNetwork.fetchCurrent()` вернёт `nil`, пока у приложения нет ещё
  и **активного разрешения на геолокацию "При использовании"** — так Apple
  ограничивает доступ к SSID/BSSID отдельно от entitlement'а. Поэтому
  `WiFiSecurityInfo` дергает `CLLocationManager` (`LocationAuthorizer`) и
  запрашивает это разрешение — саму геопозицию инструмент не использует и
  никуда не отправляет, это чисто техническое требование конкретно этого
  API. Экран теперь различает три причины неудачи: реально нет Wi-Fi, не
  дали доступ к геолокации, или (если и то и другое есть, а данных всё
  равно нет) — вероятно entitlement не подхватился при переподписи через
  iLoader на свободном Apple ID; последнее не проверено на реальном
  устройстве до конца.
- ARP-spoofing/MITM-детектор сознательно не делали — та же причина, что
  убила MAC-адрес: без доступа к ARP-таблице ядра нечем ловить чужие
  IP/MAC подмены, а бутафорская "детекция", которая ничего реально не
  проверяет, вреднее, чем её отсутствие.

### Известные ограничения

- iOS с 14-й версии требует явно перечислять типы Bonjour-сервисов в
  `Info.plist` (см. `NSBonjourServices` в `project.yml`) — сканировать
  вообще все сервисы, как это может делать Fing на настроенном роутере,
  нельзя без этого списка.
- Для первого запуска на устройстве потребуется разрешение
  "Локальная сеть" (сработает автоматически по `NSLocalNetworkUsageDescription`).
- MAC-адрес/вендор есть, но с оговорками (спуфинг на части устройств,
  зависимость от переподписи) — см. отдельный раздел выше.
- Нет полного скана соседних Wi-Fi точек — см. "Инструменты безопасности" выше.

## Сборка (нужен Xcode → значит нужен Mac)

Проект держится как обычные Swift-файлы + `project.yml` для
[XcodeGen](https://github.com/yonaskolb/XcodeGen), а не как бинарный
`.xcodeproj` — так удобно редактировать код где угодно (в том числе тут, в
Linux), а сам `.xcodeproj` генерируется по требованию.

### Вариант A — есть доступ к Mac (свой/чужой/облачный)

```bash
brew install xcodegen
cd appleapp
xcodegen generate
open NetScan.xcodeproj
```

Дальше как обычно: выбираешь свой Apple ID в Signing & Capabilities,
подключаешь iPhone, жмёшь Run.

### Вариант B — совсем без Mac и бесплатно: GitHub Actions

GitHub Actions с macOS-раннером **бесплатен и безлимитен для публичных
репозиториев** (для приватных — урезанная квота из-за x10 множителя на
macOS-минуты). Воркфлоу уже лежит в
[`.github/workflows/build.yml`](.github/workflows/build.yml):
он генерит проект через XcodeGen, собирает архив **без подписи**
(`CODE_SIGNING_ALLOWED=NO`) и упаковывает `.app` в `NetScan-unsigned.ipa`
как build-артефакт — платный Apple Developer аккаунт для этого не нужен.

Чтобы запустить:

1. Запушь репозиторий на GitHub как **публичный**.
2. Вкладка **Actions** → выбери workflow **"Build unsigned IPA"** →
   **Run workflow** (или просто пушь в `main` — триггерится сам).
3. Через пару минут в этом же запуске внизу будет артефакт
   **NetScan-unsigned-ipa** — скачай его, там `NetScan-unsigned.ipa`.
4. Этот неподписанный `.ipa` скармливаешь своему iLoader — он подписывает
   его твоим бесплатным Apple ID локально при установке на телефон (так
   же работают Sideloadly/AltStore). Из-за ограничения бесплатного Apple ID
   приложение придётся переустанавливать/переподписывать раз в 7 дней —
   это ограничение Apple, а не наше, и то же самое было бы с любым другим
   бесплатным способом сайдлоада.

## Дальнейшие шаги

- Резолвить IP из результатов Bonjour и мёржить в общий список устройств
  (сейчас `mergeBonjourName` — заглушка).
- Reverse DNS для `hostname`.
- Пуш-уведомление на "новое устройство в сети" (актуально для домашней
  безопасности — как раз то, за что Fing просит подписку).
- Результаты глубокого скана сейчас живут только в открытом экране деталей
  и не сохраняются обратно в общий список устройств — при повторном заходе
  на устройство скан прогоняется заново.
- Трассировка (traceroute, как в Fing) технически возможна на той же базе,
  что ICMPPinger — увеличивать TTL и ловить ICMP time-exceeded — но не
  сделана: это ещё один раунд низкоуровневого сокет-кода, а его уже
  накопилось прилично для одной сессии без Mac под рукой для локальной
  проверки сборки.
- MAC-адрес/вендор — см. "MAC-адрес и вендор (как в Fing)" выше.
